# onema-access — права на запись (record-level)

Форк Onema, ADR-003. Модуль добавляет к правам Twenty на объект и поле свой
слой «кто какие записи видит». Правила — данные: JSON-файл в репозитории,
путь задаётся переменной `ONEMA_ACCESS_RULES_PATH`. Переменная не задана —
поведение апстрима без изменений.

## Release gate: пока только стенд

Правила **применяются** только при `ONEMA_ACCESS_ENFORCE=1`. Без этой
переменной файл читается и проверяется (ошибка в нём остановит процесс), но
ни один запрос не фильтруется.

Так сделано намеренно: ONE-110 закрыл чтение, ONE-111 — запись, ONE-112 —
полиморфные связи. Пока не влит ONE-113 (realtime, CI-сверка вызовов мимо
хука, полный прогон матрицы rls-design §11), `ONEMA_ACCESS_ENFORCE=1`
ставится только на стенде.

Два пункта обязательны до включения в проде и числятся за ONE-113 (подробно —
`docs/onema/handover/2026-10-08-one-110-review-3.md`):

1. **Инвентаризация `shouldBypassPermissionChecks`.** Флаг возвращает
   управление раньше хука и выставлен в 119 файлах `twenty-server/src`. Пока
   они не перечислены и не разобраны, размер обхода не измерен.
2. **Lite-контекст.** При `lite: true` `flatRoleMaps` пуст, сверка считает
   каждую роль несуществующей и ставит `1=0` на всё. Утечки нет, но это тихий
   полный отказ джобов; все вызовы `lite: true` надо пройти.

## Как встроено в ядро

Чтение — одна точка: конец `applyRowLevelPermissionPredicates`
(`src/engine/twenty-orm/repository/workspace-repository.ts`). Через неё
проходят все SELECT и COUNT ORM и критерии UPDATE/DELETE, значит закрыты
GraphQL, REST, поиск, Cmd+K, экспорт CSV, связи, группировки и агрегаты.
Правило навешивается на главный алиас и на каждый join/exists-алиас запроса.

Запись (ONE-111) — четыре хука на собственных путях записи репозитория:

| Хук | Когда | Что закрывает |
|---|---|---|
| `applyOnemaOwnerDefaults` | до оператора вставки | владелец, которого роль не вправе написать сама |
| `assertOnemaProtectedFieldsAreWritable` | до оператора | Т-1: поля, которые пишет только приложение |
| `assertOnemaFrozenFieldsAreUnchanged` | под `SELECT … FOR UPDATE` | Т-2: заморозка, сравниваемая по заблокированной строке |
| `assertOnemaWrittenRecordsAreAccessible` | после оператора, в той же транзакции | точка №4: строка видна автору, и Б5: на чей объект она повешена |

Заморозка и защищённые поля смотрят не только на `update`: мягкое удаление и
восстановление — это запись в `deletedAt`, и правило, назвавшее это поле, их
видит. Строка, которую лок не вернул (удалена параллельно), — отказ, а не
сравнение по незаблокированному снимку.

Пятый — `assertOnemaRawSqlIsPermitted`. Сырых исполнителей два, и хук стоит на
обоих: `WorkspaceRepository.executeRaw` и `WorkspaceTransactionScope.executeRawQuery`
(`twenty-orm/datasource/workspace-data-source.ts`). Сырой SQL не проходит ни
один из четырёх хуков, поэтому DML по таблице, которую ведут правила, запрещён
(см. ниже). Единственная аудируемая сырая запись — приватный путь вставки
самого репозитория, уже прошедший все четыре хука; оба исполнителя и список
вызывающих держит CI-проверка `__tests__/onema-raw-write-guard.spec.ts`.

Realtime (ONE-113) — точка №3, издатель подписок
(`subscriptions/object-record-event/object-record-event-publisher.ts`). Событие
несёт саму запись: дифф строки ленты, поля лида. Поэтому список записей, который
издатель уже сузил правами апстрима, сужается второй раз нашим условием —
`SELECT id … WHERE id IN (:ids) AND <условие подписчика>`, пересечение, и
подписчику уходит то, что осталось.

Подписчик — не тот, кто писал. Издатель работает внутри запроса автора записи,
а спрашивать надо про роли того, кто подписан, поэтому субъект передаётся
явным полем `subject` в scope, а не выводится из `authContext`. Это
единственное место, где субъект — не вызывающий (rls-design §4).

**Событие полного удаления (`destroyed`) не доставляется**, пока правила
включены: строки уже нет, условие по ней не вычислить, а в событии лежит её
содержимое. Выбор закрытый: подписчик не узнает об удалении до следующего
запроса. Мягкое удаление и восстановление доставляются как обычно — строка на
месте, и наш `SELECT` не навешивает фильтр по `deletedAt`.

Отказ — `PermissionsExceptionCode.ONEMA_WRITE_DENIED`, а не `PERMISSION_DENIED`:
для вызывающего это тот же 403, но инвариант продукта отличим от обычного
отказа в правах. Это не косметика — `resolveWritableRecordIds` глушит
`PERMISSION_DENIED` в пустой список, что для инварианта означало бы тихо
выбросить отказанные строки и записать остальные.

Чего модуль **не** делает: предиката на сыром `SELECT` (чтение сырым SQL не
ограничивается — см. «Сырой SQL») и точки №2, кнопки «можно править», которая
остаётся за отдельной задачей после v1.

## Сырой SQL

Целевые таблицы читаются из самого оператора, а не из репозитория, через
который он пришёл: репозиторий незащищённого объекта мог бы выполнить
`UPDATE "workspace_x"."_opportunity"`. Разбираются `INSERT INTO`, `UPDATE`,
`DELETE FROM`, `MERGE INTO`, `TRUNCATE` (со списком) и `COPY … FROM` — с `ONLY`,
со схемой и без, внутри изменяющего CTE и после точки с запятой. Имя без схемы
сверяется по одной таблице: это закрытая сторона вопроса.

Отказывается целиком, какую бы таблицу ни называло: тело в долларовых кавычках,
`DO`-блок, `CALL`, `EXECUTE`. `ON CONFLICT DO NOTHING/UPDATE` блоком не
считается — строка, которую трогает эта ветка, та самая, которую `INSERT` уже
назвал. Запись, цель которой разобрать не удалось, тоже отказывается.

Строковые литералы, кавычки идентификаторов, долларовые кавычки и комментарии
разбираются одним проходом, а не по очереди: вырезание комментариев первым
принимало `/*` внутри литерала за начало комментария, и
`SELECT '/*'; UPDATE …; SELECT '*/'` читался как безобидный SELECT. Незакрытая
конструкция — отказ: где она кончалась бы, сказать нечем.

Оператор разбирается лексером, а не регулярками: регулярка видит имя там, где
Postgres видит лексическую форму. `UPDATE U&"_opportunity" SET …` пишет в
таблицу, а регулярка останавливалась на `U` и докладывала запись в таблицу
«u» — под правилами её нет, и запрос проходил. Теперь `U&"…"` раскрывается
(`\XXXX`, `\+XXXXXX`, свой символ из `UESCAPE`), `""` внутри кавычек — это одна
кавычка имени, а нераскрываемые экранирования дают отказ. Таблица под правилами,
названная так, отказывается как таблица под правилами; не названная правилами —
всё равно отказывается: экранирования раскрывает наш декодер, а не Postgres, и
«вот эта форма безобидна» — не тот ответ, который здесь можно дать.

Fail-closed по цели: каждое пишущее ключевое слово обязано дать таблицу. Форма,
которую разобрать не удалось (`UPDATE SET …`, `INSERT` без `INTO`, `COPY` без
`FROM`/`TO`, список `TRUNCATE` с чем-то, что не имя), — отказ, даже если соседний
оператор того же запроса разобрался. Запрос `COPY (…) TO` читает, но его
подзапрос может быть изменяющим с `RETURNING` — он разбирается наравне с
верхним уровнем.

`SELECT … FOR UPDATE` и `FOR SHARE` разрешены: заморозка так и читает строку,
которую сравнивает. Чтение не ограничивается — предикат на сыром `SELECT` это
вопрос ONE-113.

## Формат правил

```jsonc
{
  "roles": { "<ключ роли>": "<universalIdentifier роли Twenty>" },
  "requiredObjects": ["<nameSingular объекта>"],
  "objects": {
    "<nameSingular объекта>": { "<ключ роли>": <условие> }
  }
}
```

`requiredObjects` — список объектов, у которых правило обязано быть. Объект,
которого нет в `objects`, работает по правам апстрима (см. «Умолчания»), и это
неотличимо от «правило ещё не написали». Перечисленный здесь объект без
правила — или с правилом, в котором не названо ни одной роли, — отвергает
**весь файл**: процесс не стартует, а работающий закрывает все записи. Ключ
обязателен; «ничего не обязательно» пишется как `[]` явно, иначе забытый ключ
был бы тем же умолчанием этажом выше.

Роль опознаётся по `universalIdentifier`, а не по id и не по названию:
runtime id меняется при пересоздании роли, название переименовывается в UI
(rls-design §4). Два ключа на один `universalIdentifier` отвергаются — это
объединение условий, то есть расширение прав.

Условия:

| Условие | Смысл | SQL |
|---|---|---|
| `{ "all": true }` | без ограничений | условие не добавляется |
| `{ "eq": ["<поле>", "$me"] }` | поле указывает на участника | `"alias"."<колонка>" = :param` |
| `{ "eq": ["<поле>", <значение>] }` | строка, число, `true`/`false`, `null` | `=` или `IS NULL` |
| `{ "exists": { "object", "backForeignKey", "where"? } }` | есть запись `object`, видимая этой же роли, у которой `backForeignKey` ссылается на эту | `EXISTS (SELECT 1 … AND <правило object> AND <where>)` |
| `{ "parent": { "foreignKey", "object" } }` | родитель по ключу виден этой же роли | `EXISTS (SELECT 1 … AND <правило родителя>)` |
| `{ "anyParent": { "parents": [{ "foreignKey", "object" }, …] } }` | полиморфная связь: видна хотя бы одна заполненная цель | `OR` по веткам, каждая — как `parent` |
| `{ "linked": { "objectIdField", "recordIdField", "objects": [...] } }` | запись-источник, названная id метаданных объекта и id строки | `OR` по объектам: `<objectIdField> = :id AND EXISTS (…)` |
| `{ "and": [...] }`, `{ "or": [...] }` | склейка | скобки |

Имя поля — поле объекта: для связи берётся её join-колонка (`owner` →
`"ownerId"`), иначе имя колонки как есть. У `linked` оба поля — обычные
колонки-идентификаторы, не связи: связь там означала бы сравнение join-колонки
с id метаданных объекта, то есть тихо пустую ленту, и файл отвергается.

### Полиморфные связи

`attachment`, `note`, `noteTarget`, `taskTarget` и `timelineActivity` связаны
с карточкой не одним внешним ключом, а набором `target*Id`
(rls-design §3.1). Для них:

- **Цель, названная в `anyParent` или `linked`, обязана иметь своё правило.**
  Обычный `parent` на объект без правила ограничений не вносит, и это
  осознанно (см. «Умолчания»). Внутри полиморфного условия то же молчание —
  дыра: ветки соединены через `OR`, и одна цель без правила открывает все
  записи, которые на ней висят. Файл с такой целью не загружается.
- **Ни одна цель не заполнена — запрет.** Сирота видна только ролям с `all`.
- **`linked` на объект, которого нет в списке, и пустое поле — запрет.**
  Строка ленты несёт дифф чужой записи; про объект, о котором решения нет,
  решение — «закрыто».
- **Глубина через полиморфную цель — четыре объекта вместо трёх.**
  Полиморфный переход — наша косвенность, а не уровень модели: вложение
  висит на карточке, между ними ничего нет. При лимите в три карточка, чьё
  собственное правило уже достаёт до трёх объектов, не могла бы иметь правил
  на свои вложения — ровно цепочка `attachment → person → company →
  opportunity` (access-matrix §1.2, §1.3). Лимит поднимается один раз, а не
  на каждый переход, и цепочка в пять объектов по-прежнему отвергается при
  загрузке.
- **Заметка создаётся раньше своей цели.** Правило из одного
  `exists noteTarget` отвергло бы то самое создание, которое защищает: у
  новой заметки целей ещё нет. Поэтому в примере у `note` вторая ветка —
  `eq ["createdByWorkspaceMemberId", "$me"]`: автор видит свою заметку
  всегда, а привязать её к чужой записи всё равно не может — это закрывает
  правило `noteTarget`.

### `writeRequiresParentAccess` на полиморфном объекте

Ключ ONE-111 (Б5): объект → список связей `{foreignKey, object}`. Родитель,
названный такой связью, обязан пройти собственное правило того же автора в
той же транзакции. Связи соединяются через `AND`, и каждая читается как
«ключ пуст **или** родитель виден», поэтому набор из нескольких связей — это
в точности полиморфный набор: заполнен не больше одного ключа, остальные
ветки проходят сами собой. Это запись-зеркало `anyParent`: там `OR` по
заполненной цели, здесь `AND` по всем объявленным.

- **Глубина.** Несколько связей на одном объекте считаются полиморфным
  набором и получают тот же бюджет, что и `anyParent` этого объекта. Одна
  связь — обычный внешний ключ, обычный лимит.
- **Цикл.** Цепочка начинается со строки, которую пишут, а не с правила:
  когда правило родителя снова доходит до этого объекта, оно читает другие
  его строки под их собственным правилом и на этом останавливается. Поэтому
  первый возврат к исходному объекту циклом не считается — `projectMember →
  project → projectMember` это то, как подрядчик вообще видит проект; второй
  возврат снова цикл (подробно — «Проверка файла»). Обход по-прежнему
  ограничивает глубина.
- **Чего ключ не закрывает.** Если правило родителя удовлетворяется той
  самой строкой, которую пишут, второй проход ответит «да». Так устроена
  пара `note` ↔ `noteTarget`: `note` видна, потому что у неё есть видимая
  цель, и объявить `noteTarget → note` значит спросить правило, которое новая
  цель уже выполнила. В примере такой связи поэтому нет; см. «Открытые
  вопросы» хендовера ONE-112.

## Умолчания

- Объекта нет в `objects` — работают только права Twenty на объект и поле.
- Объект есть, роли участника нет — **запрет**: закрыто по умолчанию.
- У участника несколько ролей — условия объединяются через `OR`.
- `$me` неизвестен (API-ключ, приложение) — условие ложно.
- `parent` ложен при пустом внешнем ключе: запись-сирота видна только ролям
  с `all`.
- `exists` и `parent` симметричны: запись-свидетель — обычная запись своего
  объекта и подчиняется его собственному правилу. `{"exists": {"object":
  "project"}}` не обходит правило `project`; если `project` закрыт для роли,
  всё условие ложно. Объект, которого нет в `objects`, ограничений не вносит.
- `shouldBypassPermissionChecks` — **правило видимости** не применяется: это
  единственный доверенный обход, и его явно запрашивает вызывающий при создании
  репозитория. Отдельного обхода по `authContext.type === 'system'` нет:
  `buildSystemAuthContext` вызывается примерно из 140 мест (workflow-действия,
  AI-инструменты, лента, почта), системный контекст сам по себе ничего не
  доказывает. Дошедший до хука системный контекст ролей не имеет — объект под
  правилом закрывается.
- **Инварианты записи bypass не выключает.** За флагом прячутся два разных
  вопроса, и смешивать их нельзя:
  - «увидит ли этот актор эту строку» — право, и вызывающий с bypass на него уже
    ответил;
  - «можно ли писать это поле вообще» (`writeProtectedFields`, `freezeWhen`) и
    «можно ли вешать эту строку на этот объект» (`writeRequiresParentAccess`) —
    инварианты продукта. Членство, созданное в чужом проекте, отдаёт проект
    одинаково под воркером и под ролью sales. Сырой DML по таблице под правилами
    запрещён и под bypass тоже.

  Единственное исключение — актор, которого называет сам файл (`application`):
  наше приложение, пишущее от имени системы. Без bypass оно остаётся обычным
  вызывающим, и инвариант действует на него как на всех.

  **Это осознанная доверенная граница, а не недосмотр** (решение оркестратора,
  раунд 4 ревью). `writeRequiresParentAccess` спрашивает «виден ли родитель
  автору записи», а у токена приложения нет `$me`: автоматизации
  deal-to-project и project-launch создают связи от имени системы и упёрлись бы
  в правило, которое для них не может быть истинным ни при каких данных.
  Граница держится на другом: код функций приложения лежит в репозитории и
  проходит ревью, а `application` — это конкретный `universalIdentifier` в файле
  правил, а не «любой системный контекст». Что это **не** покрывает: функция
  приложения с ошибкой может повесить запись на чужого родителя, и ни один хук
  этого не поймает. Т-1 (`writeProtectedFields`), Т-2 (`freezeWhen`) и запрет
  сырого DML на приложение распространяются полностью — исключение ровно одно.
- `ownerDefaults` подставляет владельца и тогда, когда вызывающий прислал поле
  явным `null`. Это намеренно: запись этого объекта без владельца невидима той
  самой роли, ради которой умолчание и существует, так что проверка после записи
  всё равно отказала бы в создании. Роль, которой запись без владельца
  действительно нужна, — это роль, для которой файл не называет `ownerDefaults`.
- Запрет на чтении — это пустой результат (`1=0`), а не ошибка прав: роль,
  которой объект разрешён, получает ноль строк, а не 403. Запрет на записи —
  наоборот, ошибка: вызывающий просил что-то изменить и должен узнать, что
  этого не произошло.

## Проверка файла

Файл читается при старте (`main.ts`, `queue-worker.ts`) и дальше
перечитывается раз в несколько секунд. Нечитаемый файл, невалидный JSON,
лишние ключи, отсутствующий `requiredObjects`, обязательный объект без
правила, цель `anyParent` или объект `linked` без собственного правила, роль
без объявленного `universalIdentifier`, два ключа на одну роль, цикл,
вложенность глубже трёх объектов — четырёх, если путь прошёл через
полиморфную цель (`parent`, `exists`, `anyParent` и `linked` считаются
одинаково) — или больше 1024 условий в одном правиле: сервер не стартует.
Лимит условий считает весь статический обход — правила **всех** ролей
**всех** достижимых объектов, — а не тот SQL, который соберётся для
конкретного участника: полиморфное правило обход умножает. Работу, которую
вызывает одна строка, ограничивает глубина, а не это число.
Циклы и глубина считаются по всем ролям сразу, а не по одной: компилятор
объединяет через `OR` правила всех ролей участника, поэтому цепочка
`A (роль x) → B (роль y) → A` — настоящий цикл в SQL, и файл с ней
отвергается при загрузке, а не вырождается в тихий запрет на лету.

Связи `writeRequiresParentAccess` обходятся так же (иначе слишком глубокая
связь становилась тихим `denied`, а на стороне записи это читается как «этот
внешний ключ должен остаться пустым»), но с одним исключением: цепочка
проверки родителя начинается со строки, которую пишут, а не с правила. Когда
правило родителя снова доходит до этого объекта, оно читает другие его строки
под их собственным правилом и там и останавливается, так что
`projectMember → project → projectMember` циклом не является — это то, как
подрядчик вообще видит проект. Исключение действует только для объекта, которым
цепочку засеяли, и ровно на один возврат: второй (`… → projectMember →
project → projectMember`) снова цикл. Глубина по-прежнему ограничивает обход —
при нынешнем пределе в три объекта второй возврат просто не успевает
запроситься, и счёт посещений нужен, чтобы инвариант не зависел от этого числа.
Если файл перестал разбираться уже на ходу, процесс не откатывается к
«правил нет»: все записи закрываются, и причина пишется в лог.

Вторая проверка — против метаданных воркспейса, при первом применении:
объекты, поля, целевые объекты `exists`/`parent`/`anyParent`/`linked`, роли и
топология связей (`exists.backForeignKey` должен быть связью обратно на
исходный объект, `parent.foreignKey` и каждый `anyParent.parents[].foreignKey`
— связью именно на объявленный `object`, а поля `linked` — колонками, а не
связями). Любое
несовпадение закрывает **все** записи и пишет список проблем в лог: опечатка
в имени объекта означает, что настоящий объект остался без правила, то есть
открыт, а угадать замысел нечем.

## Перечитывание правил

Каждый процесс раз в `ONEMA_ACCESS_RULES_RELOAD_INTERVAL_MS` (5 с) читает
файл, считает sha256 и, если содержимое изменилось, разбирает новую версию
целиком и подменяет её одним присваиванием — читатель видит либо старую
версию, либо новую, но не половину. Версия (12 символов хеша) пишется в лог,
так что «какие правила у этого процесса» — проверяемый вопрос.

Альтернатива («неизменяемые версии правил и обязательный скоординированный
рестарт») отвергнута: рестарт сервера и N воркеров сам по себе не атомарен, в
окне рестарта часть процессов работает по старым правилам, и ничто не
замечает процесс, который не перезапустился.

**Подменять файл только атомарно.** Записать рядом и переименовать
(`cp new /app/.../access-rules.json.tmp && mv /app/.../access-rules.json.tmp
/app/.../access-rules.json`), а не писать поверх через `scp`, `kubectl cp`
или `>`. Файл читается целиком; наполовину записанный не разбирается, и
каждый процесс, попавший в это окно, закрывает **все** записи до следующего
удачного чтения — до 5 секунд полной слепоты. `mv` в пределах одной
файловой системы атомарен, и читатель видит либо старый файл, либо новый.

## Один файл правил — один воркспейс

Файл один на процесс, а сверка с метаданными идёт по воркспейсу запроса.
Межворкспейсной утечки это не даёт (результат сверки кэшируется по identity
`flatObjectMetadataMaps` конкретного воркспейса), но воркспейс, в котором нет
объекта из `objects` или роли из `roles`, получает `invalid` и закрывает все
свои записи. То есть деплой с `ONEMA_ACCESS_RULES_PATH` фактически
однотенантный: несколько воркспейсов в одном процессе возможны, только если
все они имеют одинаковый набор названных объектов, полей и ролей.

## Подмена правил в тестах

`setOnemaAccessRulesForTesting` — мост только для тестов. Интеграционный тест
поднимает приложение в `globalSetup` Jest, а правила ставит из тестового
файла: это один процесс ОС, но разные vm-контексты Jest, поэтому общий у них
только диск — отсюда файл, а не кэш в памяти.

Файл проверяется одним `stat` на запрос, а перечитывается и разбирается,
только если изменились время изменения (в наносекундах) и размер: подмена
видна на следующем же запросе, а чужим сьютам репозитория мост стоит один
системный вызов.

Мост существует **только при `NODE_ENV=test`**. Вне тестов путь не
вычисляется вовсе: оставшийся в temp файл не может перебить боевой
`ONEMA_ACCESS_RULES_PATH`, а вызов самой функции падает с ошибкой вместо
тихой установки правил, которые никто не прочитает. Имя файла содержит pid —
общий на хост путь позволял бы одному прогону (или чему угодно, что пишет в
temp) задать права другому.

## Гонка заморозки — отдельным прогоном

Детерминированная половина вопроса Т-2 живёт в обязательном прогоне
(`test/integration/graphql/suites/onema-access/onema-write-access.integration-spec.ts`,
тест «reads the pre-image of the freeze under a row lock…»): сторонняя
транзакция держит блокировку строки и переводит запись в замороженное
состояние, а запрос, который уже прочитал свой снимок, обязан дождаться
блокировки, перечитать pre-image под ней и отказать. Чего он ждёт, видно в
`pg_stat_activity`: это `SELECT … FOR UPDATE` по таблице записи в транзакции,
открытой раньше самого оператора, — то есть в той, которая сейчас пишет. Без
лока ждёт сам `UPDATE`, и тест это показывает.

Сама гонка — девять одновременных мутаций по одной строке, где часть ответа
даёт планировщик, — вероятностная: без лока она краснела в двух прогонах из
трёх. Поэтому она вынесена в `test/integration/onema-race/` и в обязательный
прогон не входит (`jest-integration.config.ts` игнорирует эту папку).
Запускается своим таргетом:

```bash
npx nx run twenty-server:test:integration:onema-race
```

## Пример

`packages/twenty-server/onema/access-rules.example.json` — эталон формата, но
**не** эталон полноты. Комментария в нём нет: схема строгая и лишних ключей не
принимает, поэтому оговорка живёт здесь.

В `requiredObjects` — карточки (`opportunity`, `company`, `person`,
`project`, `task`, `dataRoomItem`) и объекты, которые носят их содержимое
(`attachment`, `note`, `noteTarget`, `taskTarget`, `timelineActivity`,
`onemaApprovalDecisionRecord`).

`company` и `person` в примере появились не сами по себе: без их правил
обрываются цепочки полиморфных целей — вложение на контакте или на компании
стало бы сиротой и закрылось бы всем. Их условия взяты из access-matrix §1.2
и §1.3 (`exists opportunity` с обязательным `where`, иначе сейлз видел бы
компании всех чужих лидов).

Цели `noteTarget` сужены до `targetOpportunity` намеренно. `note` достижима
через `attachment` и `timelineActivity`, поэтому путь до компании или
контакта был бы `attachment → note → noteTarget → company → opportunity` —
пять объектов, и файл бы не загрузился. Заметка на компании или контакте
остаётся сиротой, то есть закрытой, — безопасная сторона; расширять нужно
вместе с правилами `note` (rls-design §10, ONE-112).
