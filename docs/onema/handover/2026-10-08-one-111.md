# ONE-111 — проверка после записи, владелец по умолчанию, защищённые и замороженные поля

Ветка `onema/one-111-write-check` от `onema/v2.45.0`, поверх влитого ONE-110
(`ca906eec7`). Второй из четырёх PR (ONE-110…113) по ADR-003. Основание —
`docs/research/rls-design.md` §3.2, §3.3, §11 «Запись», §12а (репозиторий
`BPMN Onema`).

Без ONE-111 права на чтение из ONE-110 обходятся правкой внешнего ключа:
условие видимости проверяется по критериям запроса, а не по тому, где строка
оказалась после записи. Поэтому порядок PR обязателен.

## Что сделано

**Точка встраивания №4 — проверка после записи** (rls-design §3.2).
Записанные строки перечитываются тем же скомпилированным условием
`compileObjectAccess`, в той же транзакции. Строка, которая после записи не
видна автору, откатывает транзакцию и даёт ошибку прав. Закрывает «создал
ребёнка у чужого родителя» и «перенёс FK в чужого родителя» — оба пути, где
права на поле бессильны, потому что внешний ключ обязан быть записываемым.

Запись становится транзакционной, когда правила вообще могут применяться
(`isOnemaAccessPossiblyActive`). Если файла правил нет — состояние `absent`, и
апстримное поведение не меняется ни на шаг: без правил транзакция заводится
ровно там, где её заводил апстрим (`validationRules.length > 0`).

**Точка встраивания №5 — владелец по умолчанию** (rls-design §3.3). При
создании записи объекта, правило которого для ролей участника — ровно
`eq [поле, $me]`, пустое поле владельца заполняется `$me`. Подстановка идёт
**после** проверки прав на поле, и это намеренно: роль, которой нужен
умолчательный владелец, — это как раз та роль, которой запись в это поле
запрещена. Строка §11 «S1 создаёт лид, `owner` недоступен на запись».

**Т-1 — защищённые поля** (rls-design §12а). Ключ `writeProtectedFields` в
файле правил: поля, которые пишет только application-контекст нашего
приложения. Ролям, перечисленным в списке поля, запись разрешена сверх того;
людям и ключам API — отказ. Проверка стоит в `validateWriteIsPermitted`, через
который уже проходит каждый путь записи со списком колонок, которые собирается
тронуть.

**Т-2 — замороженные поля** (rls-design §12а). Ключ `freezeWhen`: поля,
неизменяемые, пока запись удовлетворяет условию. Старое и новое значение
сверяются **до** записи — именно то, чего не может правило проверки, которое
видит только состояние после.

**Схема правил.** Новые обязательные ключи `writeProtectedFields` и
`freezeWhen` (как `requiredObjects` из ONE-110: «ничего» пишется явным `{}`),
необязательный `application`. Разбор и сверка с метаданными воркспейса —
fail-closed. Пример — `packages/twenty-server/onema/access-rules.example.json`.

## Тесты

**Юнит — 117 зелёных** в `src/engine/onema-access` (47 из них новые):
подстановка владельца (заполняет, не трогает заданного, `null` = пусто, роль с
`all` — ничего, `$me` неизвестен, правило сложнее `eq $me`, невалидный файл —
отказ, bypass); защищённые поля (человек, ключ API, наше приложение, чужое
приложение, роль из списка, join-колонка связи, одна колонка композитного
поля); заморозка (связь, подмена файла той же формы, условие ещё не выполнено,
незамороженное поле, запись того же значения, приложение тоже не исключение);
проверка после записи (SQL и параметры, строка выпала — отказ, роль без
доступа, роль с `all` — без запроса, строка без id — отказ).

```bash
npx jest --config=jest.config.mjs src/engine/onema-access
```

**Интеграционные — 21 зелёный** в
`test/integration/graphql/suites/onema-access/` (7 новых, строки rls-design §11
«Запись»): создал — вижу (владелец подставлен); вставка владельцу-чужому —
отказ и откат; вставка к чужому родителю — отказ и откат; перенос FK в чужого

Каждый отказ проверяется в паре с контролем: «не прошло» ничего не значит,
пока то же правило не пропускает законную запись.

### Грабли прогона

**Сид нельзя считать данными теста.** Несколько апстримных наборов чистят
`company` и `person` тестового воркспейса целиком
(`test/integration/utils/delete-all-records.ts`), и всё, что запускается после
них, не находит ни одной засеянной строки. Наши наборы были зелёными в
одиночку и красными в общем прогоне. Теперь обе спеки заводят свои записи
сами (`suites/onema-access/utils/onema-access-fixtures.util.ts`), сужают к ним
все запросы и удаляют в конце.

**Nx отдаёт сброс базы из кэша.** `nx database:reset` без
`--skip-nx-cache` пропускает `truncate-db`, схемы воркспейсов остаются, и
пересев падает на `type "attachment_fileCategory_enum" already exists`. Нужен
`--skip-nx-cache`.

**`jest --shard` не воспроизводит общий прогон.** Апстримные наборы
переименовывают роль `Member` и этим ломают друг друга; шардирование меняет
порядок, и падает половина. Для сверки нужен прогон всей директории целиком.

### Результат прогона

`test/integration/graphql/suites/` после сброса базы: **274 набора из 280
зелёные, 1816 тестов из 1864**, оба наших набора в их числе. До правки спек
падали 8 наборов и 48 тестов.

Оставшиеся 6 наборов — апстримные и к форку не относятся:

- четыре набора `event-logs` и `chat-conversation-record-attachment` упираются
  в ClickHouse, которого на стенде нет (`ECONNREFUSED 8123`);
- `object-records-permissions/fields-permissions/read-permissions` и
  `chat-conversation-record-attachment` воспроизводятся в одиночку на свежей
  базе, где модуль `onema-access` полностью неактивен: правил нет, состояние
  `absent`, и все пять точек встраивания вырождаются в no-op.

Стенд: контейнеры `onema-it-pg` и `onema-it-redis` (5432/6379),
`NODE_OPTIONS=--max-old-space-size=8192`.

## Открытые вопросы

1. **Т-3 (серверная transition-команда) в ONE-111 не делали.** rls-design §12а
   помечает её «рассмотреть в ONE-111»: правило не знает, откуда лид пришёл, и
   финальность «Сделки» пока держит функция `lead-guard`, которая откатывает
   после записи. Заморозка (Т-2) закрывает подмену компании и файла договора,
   но не сам переход стадии. Решение — за владельцем: отдельная задача или
   часть ONE-112.
2. Строки §11 «upsert по уникальному полю, запись скрыта» и «письмо с `fileId`
   чужого вложения» остаются на ONE-113 (см. rls-design §13).
3. Производительность не замерена: проверка после записи — один
   дополнительный SELECT на запись в той же транзакции. Замер — стенд ONE-002.
