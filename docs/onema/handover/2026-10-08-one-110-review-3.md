## 1. Б2 — `exists` подчиняется правилу своего объекта

Замечание: `compileExists` звал `compileCondition(where)`, тогда как
`compileParent` звал `compileObjectAccess` и наследовал правило родителя.
Асимметрия направлена в сторону **fail-open**: правило
`{"exists": {"object": "project", …}}` обходило правило самого `project`.
В §5 дизайна так и было формально написано, но нигде не предупреждено, а
ONE-112 (`anyParent`, `linked`) добавит таких правил много.

Сделано: свидетель `exists` — обычная запись целевого объекта и проходит
`compileObjectAccess` по тому же объекту, как и строка, до которой дотягивается
`parent`. Целевой объект закрыт для роли — всё условие `denied`, то есть
fail-closed. Объект, которого нет в `objects`, по-прежнему ограничений не
вносит (права апстрима). Условия складываются через `AND`:
`EXISTS (… AND <правило object> AND <where>)`; параметры обеих частей
сливаются, а не перезаписываются.

Тесты: «свидетель `exists` подчиняется правилу своего объекта» (ожидаемый SQL
целиком, два параметра) и «`exists` на объект, закрытый для роли, — `denied`».

## 2. Пункт 5 — циклы и глубина по всем ролям

Замечание: разбор файла шёл по одному `roleKey`, а компилятор ORит условия
**всех** ролей субъекта. Цикл `A (роль x) → B (роль y) → A` проходил проверку
при загрузке и вырождался в тихий `denied` на лету — fail-closed, но
диагностируется только по пустым спискам.

Сделано: `walkCondition` при входе в объект обходит условия всех ролей этого
объекта, а не одной. Бюджет условий (32) остался общим на одно правило — это
честно: столько SQL компилятор и породит. Сообщения об ошибке больше не
называют одну роль, а называют правило, с которого начался обход.

Тесты: «цикл, который замыкается только через две роли» и «правило объекта, до
которого дотянулся `exists`, считается в глубину».

## 3. Пункт 4 — интеграционные тесты на запись

Хук висит на критериях UPDATE и DELETE, но все двенадцать интеграционных
тестов были только на чтение. Добавлены два (rls-design §11, S1):

- update чужой записи по id не меняет строку, а своя — меняется;
- soft-delete чужой записи не трогает строку, а своя — удаляется.

Обе стороны в одном тесте намеренно: «чужая не изменилась» ничего не доказывает
без «своя изменилась по тому же правилу». Строка читается обратно админом при
снятых правилах — правило, называющее только роль участника, закрывает объект и
для админа тоже, а вопрос здесь «что в строке», а не «кто её видит». Обе
проверки возвращают сид в исходное состояние (переименование назад, `restore`).

## 4. Пункты 6 и 7 — эксплуатация

- **Подмена файла правил только атомарно**: запись рядом + `mv`, не `scp`,
  `kubectl cp` или `>` поверх. Файл читается целиком; наполовину записанный не
  разбирается, и каждый процесс в этом окне закрывает все записи — до 5 секунд
  полной слепоты. В README и `.env.example`.
- **Один файл на процесс = однотенантный деплой**: сверка идёт по метаданным
  воркспейса запроса, межворкспейсной утечки нет (кэш по identity
  `flatObjectMetadataMaps`), но воркспейс без названного объекта или роли
  получает `invalid` и закрывает все свои записи. Отдельный раздел README.

## 5. Пункт 8 — `requiredObjects` в примере

Комментарий внутрь `onema/access-rules.example.json` не поставить: схема
строгая и лишних ключей не принимает. Оговорка живёт в README рядом со ссылкой
на пример: `requiredObjects` там — только карточки, а объекты-носители
содержимого (`attachment`, `note`, `noteTarget`, `taskTarget`,
`timelineActivity`, главная дыра §3.1) требуют полиморфных связей и
добавляются в ONE-112 — тогда же пополняется и список в примере.

## 6. Пункт 9 — тестовый мост

`fs.existsSync` на каждый запрос заменён одним `stat`; файл перечитывается и
разбирается, только если изменились mtime (в наносекундах) и размер. Наносекунды,
а не целые миллисекунды, — чтобы две подмены подряд не выглядели одной.
Попутно закрыт тихий баг: удаление override не сбрасывало кэш, и процесс мог до
5 секунд продолжать отдавать тестовые правила вместо боевого файла.

## ОБЯЗАТЕЛЬНО до включения `ONEMA_ACCESS_ENFORCE` (ONE-113)

Два пункта не делались в ONE-110 сознательно, но они **не «желательные»**:
без них включать enforcement в проде нельзя.

### Б1. Инвентаризация `shouldBypassPermissionChecks`

`workspace-repository.ts` возвращает управление до хука, когда у репозитория
выставлен `shouldBypassPermissionChecks`. Флаг ставится в **119 файлах**
`twenty-server/src`. Это не «один доверенный обход»: пока места не перечислены
и не разобраны, размер дыры не измерен, а не «принят» — оценка «принято» во
втором круге (`-review-2.md:71-78`) опиралась на непроверенное утверждение.

Что сделать в ONE-113:

1. Перечислить все 119 мест и разметить: действительно системная операция /
   маскируется под системную / случайно унаследованный флаг.
2. Для каждого «маскируется» решить: сузить до конкретной операции, заменить на
   явный серверный контекст с ролью или убрать.
3. CI-проверка на новые обращения мимо хука (запрет расширять список без
   явного разрешения).

Пока этого нет, `ONEMA_ACCESS_ENFORCE=1` живёт только на стенде.

### 3. Lite-контекст и пустой `flatRoleMaps`

`workspace-orm.manager.ts:240-244` при `lite: true` отдаёт пустой
`flatRoleMaps`. Сверка с метаданными тогда считает **каждую** роль из файла
несуществующей → `invalid` → `1=0` на всё, включая объекты, которых в правилах
нет вовсе. Утечки нет (fail-closed), но это тихий полный отказ джобов.

Выборочно проверено: `apply-calendar-events-visibility-restrictions.service.ts`
(строки 42 и 141) до хука не доходит — там стоит
`shouldBypassPermissionChecks`. Остальные ~20 вызовов `lite: true` не
проверены.

Что сделать в ONE-113:

1. Пройти все вызовы `lite: true` и определить, доходит ли путь до хука.
2. Для доходящих — либо наполнять `flatRoleMaps` в lite-контексте, либо
   отличать «ролей нет, потому что контекст урезан» от «роль не существует»
   и отказывать громко (лог + метрика), а не молча.

npx nx build twenty-shared --skip-nx-cache

# вместо nx database:reset twenty-server (см. граблю выше), из packages/twenty-server:
NODE_ENV=test node dist/database/scripts/truncate-clickhouse.js
NODE_ENV=test node dist/database/scripts/truncate-db.js
NODE_ENV=test node dist/database/scripts/setup-db.js
NODE_ENV=test node dist/command/command.js run-instance-commands --force
NODE_ENV=test node dist/command/command.js cache:flush
NODE_ENV=test node dist/command/command.js workspace:seed:dev

NODE_ENV=test NODE_OPTIONS=--max-old-space-size=8192 \
  npx jest --config ./jest-integration.config.ts --testPathPattern onema-row-access

ожидаемы: контейнера ClickHouse в этой схеме нет, на результат не влияет.
