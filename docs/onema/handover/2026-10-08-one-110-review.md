## 1 и 6. Сверка с метаданными воркспейса

Новый `utils/validate-onema-access-rules-against-metadata.util.ts`. Перед
применением правила сверяются с метаданными: объекты, поля, целевые объекты
`exists`/`parent`, роли (по `universalIdentifier`) и **топология связей** —
`exists.backForeignKey` должен быть связью целевого объекта обратно на
исходный, `parent.foreignKey` — связью именно на объявленный `parent.object`,
а не просто существующим полем.

Несовпадение делает весь файл неприменимым: все записи закрываются (`1=0`),
список проблем идёт в лог. Точечно закрыть нельзя — опечатка `opportuntiy`
как раз и означает, что настоящий `opportunity` остался вовсе без правила,
то есть открыт, а угадать замысел нечем. Это сознательно грубый отказ: его
цена — заметность, и он виден с первого запроса.

Результат сверки кэшируется по тройке «`flatObjectMetadataMaps` ×
`flatRoleMaps` × хеш файла правил»: все три заменяются целиком, поэтому
устаревшая запись недостижима, а не ошибочна.

Компилятор дополнительно обёрнут `try/catch`: исключение при компиляции тоже
даёт пустой результат, а не 500.

## 2. Резолвер ролей

По rls-design §4: роли берутся из `RolePermissionConfig` репозитория
(`resolveRolePermissionConfig` → `getRoleIdsFromRolePermissionConfig`), а не
из `authContext` напрямую, и сопоставляются с правилами по
`universalIdentifier` роли через `flatRoleMaps.universalIdentifierById`.

Диффа ядра на это ушло 8 строк: `flatRoleMaps` протянут в
`ORMWorkspaceContext` (`workspace-orm.manager.ts`, ключ кэша воркспейса уже
существовал) и в `WorkspaceInternalContext`
(`workspace-data-source.service.ts`).

Схема: значение роли — непустая строка, а не uuid (`universalIdentifier` у
роли приложения не обязан быть uuid); зато неизвестная воркспейсу роль
отсекается сверкой из п. 1, что строже проверки формы. Два ключа на один
`universalIdentifier` отвергаются при разборе: это объединение условий, то
есть расширение прав.

Интеграционный тест больше не ищет роль по UI-label `Member`: он берёт из
`getRoles` ту роль, в чьих `workspaceMembers` есть сид-участник Jony, и её
`universalIdentifier`.

## 3. Системный обход: инвентаризация

Обход по `authContext.type === 'system'` **убран**. Инвентаризация по
AGPL-коду (`packages/twenty-server/src`, clean-room: только имена файлов):

- `buildSystemAuthContext` (`core-modules/auth/utils/`) вызывается примерно
  из **140 файлов**: workflow-действия (`mail-sender`, `send-chat-message`,
  `delay`), триггеры и runner workflow, AI-инструменты
  (`dashboard/tools/*`, `workflow-tools/*`, `tool/tools/email-tool`),
  лента (`timeline/*`), почта и календарь (`messaging/*`, `calendar/*`),
  `contact-creation-manager`, `record-share`, `short-link`,
  `record-position`, `billing`, upgrade-команды, dev-seeder.
- Явный `shouldBypassPermissionChecks: true` встречается примерно в **120
  файлах** — это и есть настоящая доверенная граница, и её сужение —
  работа ONE-113 (CI-сверка вызовов мимо хука).
- `resolveRolePermissionConfig` (который превращает системный контекст в
  обход) вызывается из 12 файлов, из них точка входа GraphQL/REST —
  `api/common/common-query-runners/common-base-query-runner.service.ts`:
  для пользовательского контекста она даёт `{ intersectionOf: roleIds }`,
  не обход.

Вывод: `type: 'system'` сам по себе ничего не доказывает. Единственная
доверенная точка — явный `shouldBypassPermissionChecks`, который запрашивает
вызывающий при создании репозитория; апстрим и так выходит из
`applyRowLevelPermissionPredicates` до нашего хука в этом случае. Системный
контекст, дошедший до хука, ролей не имеет — объект под правилом
закрывается.

Тесты: `system` без обхода → `1=0`; `application` с ролью, но без `$me` →
`1=0`; API-ключ без `$me` → `1=0` (юнит, `apply-onema-row-access.util.spec`).
Интеграционный вариант этих же строк §11 (реальный API-ключ с ролью) — в
ONE-113 вместе с остальной матрицей.

## 4. Глубина, циклы, число условий

`exists` теперь добавляет целевой объект в путь — и при разборе файла, и при
компиляции. Цепочка вложенных `exists` и смешанная `exists → parent →
exists` считаются той же глубиной (≤ 3 объектов) и так же отсекаются по
циклу. Добавлен лимит `ONEMA_MAX_CONDITIONS_PER_RULE = 32`: каждое условие —
отдельный коррелированный подзапрос.

Тесты: три вложенных `exists`; смешанная цепочка; `exists`, возвращающийся к
уже пройденному объекту; правило из 64 условий.

## 5. Имена параметров

К префиксу добавлен порядковый номер компиляции, монотонный в пределах
процесса: `:onema_<n>_<alias>_p0`. Алиасы `task-owner` и `task_owner`
санитайзятся в одно имя, а query builder сливает параметры при `clone()` и
`copyWhereFrom()`, поэтому алиаса не хватает — поздний `setParameters()`
затирал значение первого условия. Для детерминизма тестов есть
`resetOnemaParameterNamespaceForTesting()`.

## 7. Кэш: выбран reload, не рестарт

Реализовано перечитывание: каждый процесс раз в 5 секунд читает файл,
считает sha256 и при изменении разбирает новую версию целиком, после чего
подменяет её одним присваиванием (parse-then-swap) — читатель видит либо
старую версию, либо новую.

Почему не «неизменяемые версии + обязательный скоординированный рестарт»:
рестарт сервера и N воркеров сам по себе не атомарен (в окне рестарта часть
процессов работает по старым правилам), и ничто не замечает процесс, который
не перезапустился. Перечитывание сводит все процессы к одной версии без
действия оператора, а версия (12 символов хеша) в логе делает вопрос «какие
правила у этого процесса» проверяемым. Цена — одно чтение небольшого файла
раз в 5 секунд на процесс.

Файл, переставший разбираться на ходу, не откатывается к «правил нет»:
состояние `failed` закрывает все записи и громко логируется.

## 8. Алиас без table shape

Раньше такой алиас молча пропускался. Теперь запрос закрывается целиком
(`1=0` на главный алиас) с ошибкой в логе: алиас, таблицу которого мы не
знаем, — это алиас, который нельзя сверить с правилами. Интеграционно
покрыты вложенная связь (`company { people }`), фильтр и сортировка по связи
(одна таблица под несколькими алиасами одного запроса) и join закрытого
объекта.

## 9. Release gate

Правила **применяются** только при `ONEMA_ACCESS_ENFORCE=1`. Без переменной
файл читается и проверяется (ошибка останавливает процесс), но ни один
запрос не фильтруется. `ONEMA_ACCESS_ENFORCE=1` без
`ONEMA_ACCESS_RULES_PATH` тоже останавливает процесс.

**До влития ONE-111…113 переменная ставится только на стенде.** Причина в
README модуля и в `.env.example`: один ONE-110 закрывает чтение, но не
запись — права на чтение обходятся правкой внешнего ключа (ПМ переносит
задачу в чужой проект, и она уезжает вместе с правами).

## EXPLAIN и индексы

Вынесены из ONE-110 и оформлены как требование к модели данных (ONE-101):
объектам под правилами нужны FK-индексы, для `exists` — partial по
`(<fk>) WHERE "deletedAt" IS NULL`. Замер `EXPLAIN ANALYZE` на целевых
объёмах — стенд ONE-002. Ограничение глубины и числа условий (п. 4) — та
часть, которая относится к коду, и она сделана.

**Юнит — 52 теста, зелёные** (было 29).

```bash
npx jest packages/twenty-server/src/engine/onema-access \
  --config=packages/twenty-server/jest.config.mjs --rootDir=packages/twenty-server
```

Новое: сверка с метаданными (7), release gate, алиас без shape, неизвестный
объект → `1=0`, `system`/`application` без обхода, уникальность роли,
коллизия алиасов, глубина `exists` и лимит условий, перечитывание файла и
fail-closed при порче файла на ходу.

**Интеграционный — 11 тестов, зелёные** (было 8). Добавлены: вложенная связь
под сузившимся списком, фильтр и сортировка по связи, неизвестный объект в
правилах → пусто. Роль больше не ищется по label.

Прогон как в прошлый раз: одноразовые контейнеры `onema-it-pg`
(postgres:16) и `onema-it-redis` (redis:7) на 5432/6379, удалены после.
Отличие от прошлой сессии: базу `test` пришлось создать руками
(`CREATE DATABASE test`) — `database:init` на пустом контейнере падает в
`InitPostgres` раньше, чем успевает её создать.

```bash
docker run -d --rm --name onema-it-pg -p 5432:5432 \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=default postgres:16
docker run -d --rm --name onema-it-redis -p 6379:6379 redis:7
docker exec onema-it-pg psql -U postgres -c "CREATE DATABASE test;"
npx nx build twenty-shared --skip-nx-cache
NODE_ENV=test npx nx database:reset twenty-server
NODE_ENV=test npx jest --config ./jest-integration.config.ts --testPathPattern onema-row-access
```

Соседние прогнаны и зелёные: `twenty-orm` и `onema-access` юнит (641 тест),
интеграционные `relation-join-rls`, `permissions-on-relations`,
`twenty-orm` (9 тестов).

**Та же граблина, что и в прошлый раз:** `nx database:reset` тянет
`twenty-ui:build`, который падает на `vite-plugin-checker`
(`TS5042: Option 'project' cannot be mixed with source files`). Обходится
временным отключением чекера в `packages/twenty-ui/vite.config.ts` (не
коммитится). Нужен отдельный тикет.
