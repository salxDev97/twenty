# ONE-114 — серверная проверка переходов статуса

Ветка `onema/one-114-transitions` от `origin/main` (форк
`salxDev97/twenty`; `main` уже несёт ONE-110…113). Основание —
`docs/research/rls-design.md` §12а Т-3/Т-7 (репозиторий `BPMN Onema`) и
`docs/hardening.md` п. 3–5.

Закрывает:

- **п. 3** — переходы статуса сметы через REST не защищены (DRAFT →
  ACCEPTED одним PATCH).
- **п. 4** — гонка пересчёта и решения CEO: окно между чтением и PATCH.
- **п. 5** (наполовину) — read-modify-write без CAS для статусных полей:
  переход читает pre-image под тем же блокированием строки, что заморозка
  (ONE-111); полная CAS по `updatedAt`/версии не сделана — см. «Открытые
  вопросы».

## Что сделано

**Новая секция правил `transitions`** (мандатная, как `writeProtectedFields`
и `freezeWhen`; `{}` — «ничего не ограничено»). На объект — одно поле-статус
и список рёбер графа:

```jsonc
"transitions": {
  "<объект>": {
    "field": "<поле>",
    "rules": [
      { "from": null, "to": ["DRAFT"], "roleKeys": ["sales"] },
      { "from": "DRAFT", "to": ["IN_REVIEW"], "roleKeys": ["sales"] },
      { "from": "IN_REVIEW", "to": ["CEO_APPROVED"], "roleKeys": [] }
    ]
  }
}
```

`from: null` — состояние, в котором поле ещё не было записано: эта же
граница держит создание записи (см. ниже). `roleKeys: []` — «только
приложение» (серверная команда, не роль, пишущая поле напрямую).

**Проверка `assertOnemaTransitionIsPermitted`**
(`utils/assert-onema-transition-is-permitted.util.ts`), в точности по
образцу заморозки (ONE-111):

- значение, не названное ни в одном `from`, — отказ любому переходу из
  него (fail-closed, та же логика, что у `freezeWhen`/`writeProtectedFields`);
- запись того же значения — не переход (общая с заморозкой
  `isOnemaSameWrittenValue`, вынесена в отдельный файл
  `is-onema-same-written-value.util.ts`, чтобы не дублировать код между
  заморозкой и переходом);
- актор: `application` из файла правил проходит любое ребро, человек —
  только если его роль в `roleKeys` этого ребра, API-ключ — никогда (та же
  граница, что у Т-1 в `assertOnemaProtectedFieldsAreWritable`: ключ несёт
  роль того, кто его создал, не того, кто его использует);
- создание записи — отдельная ветка без лока: строки ещё нет, `from`
  читается как `null`.

**Один и тот же лок с заморозкой.** `lock-onema-frozen-records.util.ts`
переименован в `lock-onema-guarded-records.util.ts`
(`lockOnemaGuardedRecordsForUpdate`): он берёт `SELECT … FOR UPDATE`, если
объект назван хотя бы в `freezeWhen`, хотя бы в `transitions`, или в обоих —
тогда оба хука сравнивают один и тот же заблокированный pre-image. Это и
закрывает п. 4 (гонка пересчёта/решения CEO): вторая транзакция, решающая
тот же переход, либо коммитится раньше лока (и тогда видна), либо ждёт его
и перечитывает уже изменённую строку.

В `workspace-repository.ts` приватный метод
`assertOnemaFrozenFieldsAreUnchangedUnderLock` переименован в
`assertOnemaWriteInvariantsAreSatisfiedUnderLock` и теперь после лока
вызывает оба хука (`assertOnemaFrozenFieldsAreUnchanged` и
`assertOnemaTransitionIsPermitted`) на одном и том же `lockedUpdates`. Это
покрывает `update`, `soft-delete` и `restore` (мягкое удаление/восстановление
— запись в `deletedAt`, которую видит правило, назвавшее это поле). Для
`insert` — отдельный вызов `assertOnemaTransitionIsPermitted` без лока,
сразу после применения `applyOnemaOwnerDefaults`, до вставки.

**Схема и валидация.** `transitions` — мандатный ключ (`onema-access-rules.schema.ts`).
`parse-onema-access-rules.util.ts`: `roleKeys` должны быть объявлены в
`roles`; ребро с `roleKeys: []` без `application` в файле — отказ файла
целиком (тот же принцип, что у `writeProtectedFields`); два ребра с
одинаковым `from` на одном объекте — отказ (неоднозначно, какое ребро
проверять). `validate-onema-access-rules-against-metadata.util.ts`: поле —
ровно одна колонка этого объекта (как условие `freezeWhen`).

## JSON для `apps/onema/access-rules.json` (следующая задача, в `onema-os`)

Этот PR **не трогает** `onema-os`. Когда объект `onemaEstimate` появится в
модели данных, в `apps/onema/access-rules.json` нужна секция `transitions`
вида:

```json
{
  "transitions": {
    "onemaEstimate": {
      "field": "status",
      "rules": [
        { "from": null, "to": ["DRAFT"], "roleKeys": ["sales", "projectManager", "salesHead"] },
        { "from": "DRAFT", "to": ["IN_REVIEW"], "roleKeys": ["sales", "projectManager", "salesHead"] },
        { "from": "IN_REVIEW", "to": ["CEO_APPROVED", "DRAFT"], "roleKeys": [] },
        { "from": "CEO_APPROVED", "to": ["SENT"], "roleKeys": [] },
        { "from": "SENT", "to": ["ACCEPTED"], "roleKeys": [] }
      ]
    }
  }
}
```

`IN_REVIEW → DRAFT` — возврат на доработку (решение CEO «не согласовано»),
тоже только приложением. Решения владельца, которые это предполагает и
которые должен принять кто-то, прежде чем вписывать точный JSON в боевой
файл:

1. **Кто смотрит смету на этапе DRAFT → IN_REVIEW.** Я предположил
   `sales`/`projectManager`/`salesHead` по аналогии с правом редактировать
   смету — нужно подтвердить у владельца, что отправка на согласование
   открыта тем же ролям, что и редактирование черновика.
2. Имя поля (`status` предположено) и ровный список значений
   (`DRAFT`/`IN_REVIEW`/`CEO_APPROVED`/`SENT`/`ACCEPTED`) — взяты из
   `docs/hardening.md` п. 1 буквально; модель данных сметы может назвать их
   иначе.

## Открытые вопросы

1. **CAS по `updatedAt`/версии (п. 2 задания, опционально) — не делал.**
   Механизм ONE-111 даёт pre-image под блокировкой строки, и для переходов
   этого достаточно: конкурирующая транзакция либо видит уже изменённую
   строку (и её `from` не совпадёт), либо ждёт лок. Отдельная условная
   запись по версии добавила бы защиту только для полей **вне** графа
   переходов (например, пересчёт итогов, который описан в `writeProtectedFields`,
   а не в `transitions`) — её пришлось бы вешать на другой набор полей с
   другим условием, и это не укладывается в существующую схему `freezeWhen`/
   `transitions` без нового ключа. Не делал в этой задаче, чтобы не
   расширять схему без решения владельца о форме такого ключа.
2. **`onemaEstimate` и его реальное поле статуса не существуют в метаданных
   форка.** Пример в `access-rules.example.json` и интеграционные тесты
   используют стандартные объекты/поля форка (`person.jobTitle`) как
   заместитель — тот же приём, что уже стоит у заморозки («DEAL»). Когда
   появится модель сметы (вероятно, Apps SDK модуль, упомянутый в
   `docs/hardening.md` как «Сметы #37» — в другом репозитории), правило
   нужно переписать под настоящее имя объекта/поля; JSON выше — заготовка,
   не окончательный текст.
3. **Переход стадии лида («Сделка» только приложением/по правилам
   воронки)** из задания — архитектурно выразим тем же механизмом
   (`transitions` на `opportunity.stage` или на то поле, которым ТЗ опишет
   воронку), но не сделан: в форке нет объекта/поля, которое уже означает
   «стадия лида» по ТЗ (`onemaStage` в примере — тоже заготовка ONE-111, не
   настоящая колонка). Как только модель лида определится, добавление
   графа — конфиг, не код.
4. **`transitions` не проверяет upsert отдельно от create/update.** Я не
   нашёл в существующем покрытии (`onema-write-access.integration-spec.ts`)
   пути, где upsert меняет статусное поле мимо `update`/`insert` — оба пути
   уже проходят через `performMutation`/`runBatchUpdate`, которые я
   покрыл, но отдельного интеграционного теста именно на upsert +
   transitions не писал (бюджет задачи). Юнит-покрытие проверки самой
   логики (`assertOnemaTransitionIsPermitted`) не зависит от того, как
   репозиторий до неё добрался, так что риск в основном в самой проводке —
   стоит перепроверить при следующей правке `workspace-repository.ts`.
