## 1. Недостающие строки матрицы §11 (ШАГ 2, п. 4)

Нашёл в рабочем дереве незакоммиченные правки и два новых файла прежнего
исполнителя (упёрся в лимит до коммита): тест на `groupBy`/`salesSummary`,
на allow-list почтовых вложений. Файловый токен и `Workflow` — см. ниже,
это я проверил, поправил расхождение и закоммитил
(`d03071de8`).

**Что покрыто новыми тестами:**

- **`groupBy lead + sum(amount)` / `salesSummary`** (§11, строка «итог
  отдела»). `count` группы уже сужался (`onema-row-access`), агрегат —
  второе выражение в том же запросе: сумма, которая всё ещё учитывает
  строки чужого, выдаёт участнику цифру, которую он не имеет права знать,
  одним вычитанием.
- **`Workflow, ручной запуск S1`.** Шаг читает записи репозиторием,
  собранным внутри джобы, а не внутри запроса, который нажал «запустить».
  Без привязки роли к тому, кто запустил (а не к «никому»), шаг видел бы
  либо всё, либо ничего.
- **Файл D2/A2.** Без токена — отказ; с токеном — отдаёт байты даже после
  того, как запись ушла из видимости держателя ссылки, и ровно
  `≤ FILE_TOKEN_EXPIRES_IN`, а не дольше. Правила живут в ORM, файловый
  эндпоинт — не ORM-чтение, так что это окно, а не брешь; тест делает его
  числом.

**Расхождение с матрицей, зафиксированное, а не правленное тихо:** строка
«Файл D2 по id без токена → 401» — фактический код
`FileExceptionCode.UNAUTHENTICATED` отвечает 403
(`file-api-exception.filter.ts`), и это поведение всего фора, не что-то,
что меняет этот PR. Тест поправлен на 403 (с комментарием-ссылкой), а сам
`docs/research/rls-design.md` (другой репозиторий, `BPMN Onema`) я не
трогал — задача была работать только в форке. Нужно поправить матрицу
отдельным PR в `onema-os`, как это уже сделала ONE-112 для строки про
timelineActivity-сироту.

**Что осталось не покрыто и почему — не моё решение, а отсутствие объекта:**
объекты `contractorRate` (П17), `dataRoomItem` (П18), `contractorReview`
(П20), `profilePanel` (П21), `project`, `task`, `onemaApprovalDecisionRecord`
не существуют в форке — только в примере правил
(`onema/access-rules.example.json`), это уже отмечено в открытом вопросе 4
ONE-112. Строки матрицы про них ничем не закрыть, пока нет модели данных.
`canEdit` (точка №2) не реализован вообще — нет ни одного упоминания в коде
(`grep -rln canEdit`, пусто): это, судя по всему, фронтовое/UI поле, вне
record-level записи, которой занимается этот модуль. «Logic function,
делегированный токен» не покрыт: механика похожа на Workflow (репозиторий
собирается вне запроса), но сам прогон функции идёт через
`logic-function-executor.service.ts` и сопутствующие драйверы — завести
отдельный интеграционный тест по образцу `onema-automation-path-coverage`
можно, но это отдельная, не маленькая задача; оставляю как открытый вопрос,
а не делаю наспех. «Невалидный файл правил → сервер не стартует» уже
покрыт юнитом ONE-110/111
(`load-onema-access-rules.util.spec.ts`:«stops the process when the file
cannot be used»), просто не в интеграционном слое — решил, что повторять
то же самое интеграционным тестом не добавляет уверенности.

**Грабли прогона (специфично для этой сессии).** `jest-integration.config.ts`
жёстко задаёт `maxWorkers: 1` — CLI-флаг `--maxWorkers=2` его перебивает и
ломает тесты: интеграционный стенд держит общее состояние правил доступа
(testing override на файле, именованном `process.pid`) и общую Postgres;
два файла спеки, выполняемые параллельно, гоняют установку/сброс правил
друг у друга, и тест, ожидающий сужения по роли, видит все строки. Решение
— не передавать `--maxWorkers` интеграционному раннеру вообще (конфиг сам
держит 1, памяти с запасом). Правило «jest только `--maxWorkers=2`» из
задания — это потолок, не обязательное значение; для `jest-integration.config.ts`
оно и не нужно. Отдельно нашёл и подчистил деградацию БД: из-за более раннего
(моего же) запуска с `--maxWorkers=2` несколько «refused»-записей из
`onema-write-access` реально создались (баг гонки дал доступ) и остались в
базе навсегда, так как `afterAll` чистит только то, что создал сам прогон.
Удалил вручную по имени (`DELETE ... WHERE name ILIKE 'Onema write access%'`
и аналоги) — после этого набор снова зелёный.

## 2. Оценка сборки на v2.46.0 (ШАГ 2, п. 5) — только оценка, без обновления

Наша ветка собрана на `onema/v2.45.0`, чей кончик (`a9df5c3aa`) на 85
коммитов и 1291 файл позади тега апстрима `twenty/v2.46.0`
(`9070979232c4`). Апгрейда не делал — ни одного коммита в основную ветку не
внёс; вся проверка — во временном worktree и временной ветке, обе удалены.

**Метод.** `git merge-tree --write-tree HEAD <тег 2.46.0>` — трёхсторонний
слияние на уровне деревьев, без единого файла на диске. Результат —
**0 конфликтов**: ни один файл, который правили ONE-110…113, не правил и
апстрим на пути к 2.46.0. Собрал из полученного дерева одноразовый коммит
(`git commit-tree`), поднял его в отдельном worktree
(`onema-trial-v246`, временная ветка `onema/trial-v2.46.0`), прогнал там
юнит-тесты модуля и CI-инвентарь, затем **снёс worktree, ветку и фоновый
процесс** — в основной ветке форка следов не осталось.

**Результат на дереве v2.46.0:**

- Юнит `src/engine/onema-access` — **319 из 319 зелёные**, то же число, что
  и на `v2.45.0`.
- CI-инвентарь (`onema-raw-write-guard.spec.ts`,
  `onema-write-path-inventory.spec.ts`) — зелёный: апстрим на пути к
  2.46.0 не добавил нового пути записи мимо хука и не ввёл новый сырой SQL
  раннер поверх списка, который этот инвентарь знает.
- Диапазон `a9df5c3aad…9070979232c4` **не трогает** ни один из каталогов,
  через которые проходят наши точки встраивания: `src/engine/twenty-orm`,
  `src/modules/attachment`, `src/modules/note`, `src/modules/timeline`,
  `src/engine/core-modules/tool/tools/email-tool` — у всех пустой `git diff
  --stat` на этом диапазоне.
- Новое в диапазоне, прямо касающееся апгрейда: модуль
  `src/database/commands/upgrade-version-command/2-46/` (команда апгрейда
  2.46 — переименования, формат биллинг-кредитов) — не затрагивает
  модель Onema.
- `yarn install` в чистом worktree ведёт себя как в ONE-111/112: падает на
  post-install проверке версии Node (`v26.7.0` vs `^24.5.0`), но установка
  уже состоялась — тот же обходной путь, что описан в прежних handover.
  `twenty-shared` нужно собрать явно (`npx vite build` в его каталоге) —
  без этого юнит-тесты онемы не находят `twenty-shared/types`.
- Полный `tsgo -p tsconfig.json --noEmit` по всему `twenty-server` не
  успел отработать за разумное время в одноразовом дереве (процесс снят
  вручную, память освобождена) — это не признак проблемы именно в нашем
  коде: предыдущие handover уже фиксировали, что полный прогон долгий и на
  чистом дереве упирается в несобранные соседние пакеты (`twenty-sdk`,
  `twenty-client-sdk`), а не в код `onema-access`.

**Вывод.** На уровне диффа и модульных тестов апгрейд с v2.45.0 на v2.46.0
выглядит дешёвым: ни одного файлового конфликта, ни одного падения в
собственном модуле, апстрим не трогает ни один из каталогов встраивания.
Не проверено (и не должно считаться подтверждённым по этой оценке):
интеграционный прогон на реальной БД на дереве 2.46.0 и полный
typecheck — для них нужен полноценный апгрейд-PR с собранным деревом, не
одноразовая оценка.
