# 2026-10-11 · ONE-116 — роли на паре `from → to` и цикл в разрезе роли

Ветка `onema/one-116-transition-roles` от `main` форка `salxDev97/twenty`
(`main` несёт ONE-110…115). Два независимых изменения модуля
`onema-access`, двумя коммитами:

1. **ONE-203** — роли на уровне пары `from → to` в секции `transitions`.
2. **П17** — цикл правил считается в графе одной роли, а не по паре объектов
   сразу во всех ролях.

## 1. ONE-203: роли на паре `from → to`

### Зачем

ТЗ: подрядчик завершает задачу только после приёмки ПМ. На языке переходов
это значит: из `IN_PROGRESS` подрядчик может только в `IN_REVIEW`, а штат
(CEO, COO, РОП, РУП, ПМ, сейлз) — и в `IN_REVIEW`, и в `DONE`; из
`IN_REVIEW` в `DONE` подрядчик не может никогда.

Секция `transitions` (ONE-114) этого сказать не могла: одно ребро на `from`
с одним набором `roleKeys`, а второе ребро с тем же `from` отвергается
загрузчиком как неоднозначное (и правильно — иначе «первое совпадение»
прятало бы два правила, написанных для одного состояния).

### Формат

Элемент `to` — либо значение (как было), либо
`{ "value": …, "roleKeys": [...] }`:

```jsonc
{
  "from": "IN_PROGRESS",
  "to": [
    "IN_REVIEW",
    { "value": "DONE", "roleKeys": ["projectManager", "deliveryHead"] }
  ],
  "roleKeys": ["contractor", "projectManager", "deliveryHead"]
}
```

- **Обратная совместимость.** Цель без своих ролей берёт роли ребра —
  старый файл читается ровно так же, как читался. Существующие правила
  сметы (`onemaEstimate.status` в `apps/onema/access-rules.json`) не
  тронуты.
- **Список цели заменяет список ребра, а не сужает его.** Пересечение
  сделало бы `roleKeys: []` на ребре («только приложение») молчаливым
  поглотителем любой цели, которая назвала роль. Цель может и расширить
  ребро.
- **Цель с `roleKeys: []` — «только приложение»**, даже если ребро вокруг
  названо человеческими ролями; файл с такой целью без `application`
  отвергается так же, как ребро с `roleKeys: []`.
- **Одно значение, названное в `to` дважды**, — отказ файла: раз у каждой
  цели свои роли, это та же неоднозначность, за которую отвергается
  повторённый `from`.
- **Сообщение об отказе теперь называет и цель**: `"task.onemaStatus" from
  "IN_PROGRESS" to "DONE" is driven only by roles …` (раньше — только
  `from`). Это единственное изменение в тексте ошибок.

### Файлы

| Файл | Что |
|---|---|
| `utils/read-onema-transition-target.util.ts` | новый — два прочтения элемента `to` (значение и роли) в одном месте |
| `types/onema-access-rules.type.ts` | `OnemaTransitionTarget` |
| `utils/onema-access-rules.schema.ts` | union «значение \| `{value, roleKeys}`», `strictObject` на именованной цели |
| `utils/parse-onema-access-rules.util.ts` | `validateTransitionTargets`: необъявленная роль цели, повтор значения в `to`, требование `application` по целям, а не только по рёбрам |
| `utils/assert-onema-transition-is-permitted.util.ts` | роли читаются с цели, куда идёт запись; поиск цели по индексу, а не `find` (значение цели бывает `null`) |
| `onema/access-rules.example.json` | пример `task.onemaStatus` с ролью на паре |
| `README.md` | подраздел «Роли на паре `from → to`» |

Ядра Twenty это изменение не касается вовсе: `workspace-repository.ts` не

## 2. П17: цикл в разрезе роли

### Зачем

Попытка сделать П17 в `onema-os` (`docs/handover/2026-10-10-p17-p19-access.md`,
PR #86) упёрлась в валидатор циклов: он считал цикл по паре объектов сразу во
всех ролях. Правила

- `onemaProject` для подрядчика — `exists onemaProjectMember where member = $me`
  (подрядчик видит проект только через свою строку участия),
- `onemaProjectMember` для штата — `parent onemaProject`,

каждое по себе прямая линия, но вместе образуют пару
`onemaProject ↔ onemaProjectMember`, и файл отвергался целиком.

### Что изменилось

**Цикл считается в графе одной роли.** `ObjectChain` загрузчика несёт два
пути: `objectPath` (все роли — им по-прежнему меряется глубина) и
`roleObjectPath` (объекты, пройденные правилами **одной** роли). Когда обход
переходит к правилу другой роли, путь роли начинается заново с текущего
объекта (`enterRole`).

- замкнулся путь роли → **отказ файла**, как и был: это тот же
  неограниченный join;
- замкнулся только общий путь → **обход останавливается здесь же**, без
  отказа.

Почему остановиться безопасно: такая цепочка существует только у участника,
который держит обе роли, и там компилятор обрезает её до «ни одной строки»
ровно на том шаге, где она замкнулась (`compile-onema-row-access.util.ts`,
`enterObject` → `denied`, который `OR` просто отбрасывает). Правило, в
которое ветка вложена, сохраняет всё, что имело: роль x по-прежнему доходит
до B, роль y — до A, а потерянная ветка могла только расширить путь, уже
выданный уровнем выше. Это проверено тестом компилятора «prunes only the
branch that closes a circle across two roles», который фиксирует готовый SQL:
строка участия остаётся под собственным правилом подрядчика, правило ПМ
нетронуто.

**Глубина по-прежнему считается по всем ролям сразу** — работу, которую
вызывает одна строка, задаёт вся цепочка, а не правило одной роли.

Изменён один файл модуля (`utils/parse-onema-access-rules.util.ts`) плюс
README; `closes-onema-rule-cycle.util.ts` и компилятор не тронуты —
загрузчик спрашивает ту же функцию дважды, сначала путём роли, потом общим.

## Образ

Форк этот PR **не мержит**. После мержа оркестратором нужен тег образа
**`onema-v2.45.0-onema4`**: обе половины ветки — это изменения сервера, и
правила `apps/onema/access-rules.json`, которые их используют, на образе
`onema3` не загрузятся вовсе (файл будет отвергнут схемой на
`{ "value": …, "roleKeys": … }`, то есть закроются **все** записи). Поэтому:

- PR в `onema-os` с переходами `task.onemaStatus` (ONE-203) и PR с П17
  **нельзя катить на стенд раньше `onema4`**;
- порядок: мерж форка → сборка и публикация `onema-v2.45.0-onema4` →
  обновление стендов → мерж PR-ов `onema-os`.

## Открытые вопросы

- **Цель с `roleKeys`, которую ни одна роль не может пройти**, файлом не
  отвергается (в отличие от ребра без `application`): цель, названная ролями,
  которых нет у участников, — это просто закрытый переход, и отличить
  «закрыт намеренно» от «опечатка в ключе роли» нечем. Ключ роли при этом
  обязан быть объявлен в `roles` — опечатка в самом ключе отказывает файл.
- **Кросс-ролевой цикл теперь не виден при загрузке**: у участника с обеими
  ролями ветка молча становится `denied`. Это ровно то, чего мы хотели (п. 2),
  но означает, что «почему роль x не видит B через A» перестало быть вопросом,
  на который отвечает отказ файла. Если такие пары станут частыми, стоит
  логировать обрезанную ветку на уровне компилятора — сейчас не логируется.
