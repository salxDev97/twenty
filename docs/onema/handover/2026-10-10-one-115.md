# 2026-10-10 · ONE-115 — запрет записи в дочерние по состоянию родителя

Задача: ADR-010 п.2 требует, чтобы в архивном дата-руме (`onemaDataroom.status
= ARCHIVED`) никто не писал — ни материалы (`onemaDataroomItem`), ни участники
(`onemaDataroomMember`), ни приёмки (`onemaDataroomAcceptance`) — хотя `objects`
продолжает тем же ролям разрешать их **читать**. Разбор в
`docs/handover/2026-10-10-dataroom-archive-and-errors.md` (onema-os) показал,
что у модуля `onema-access` этого примитива не было: `freezeWhen` смотрит
только на свою строку, а `objects` не различает SELECT и критерий
UPDATE/DELETE одной и той же роли.

## Что сделано

Новая секция правил `writeFrozenByParent` — зеркало `freezeWhen` для условия,
которое лежит не на самой записи, а на родителе через `foreignKey`:

```jsonc
"writeFrozenByParent": {
  "<дочерний nameSingular>": [
    {
      "foreignKey": "<поле-связь на родителя>",
      "object": "<nameSingular родителя>",
      "field": "<поле-условие родителя>",
      "equals": "<значение>",
      "allowApplication": false   // необязательно, по умолчанию true
    }
  ]
}
```

- **Проверяется и старое, и новое значение FK** — запись, оставленная под уже
  замороженным родителем, отказана так же, как перенос к замороженному
  родителю; перенос **прочь** из замороженного родителя тоже отказан (строка
  ещё читает старый FK как замороженный, пока сама запись не прошла).
- **Правило `objects` родителя не спрашивается** — в отличие от
  `writeRequiresParentAccess` (это «виден ли родитель», здесь — «что сейчас в
  его строке»), поэтому родитель не обязан иметь собственную запись в
  `objects`, и условие не входит в обход цикла/глубины `objects`.
- **Лок.** Строка родителя берётся `SELECT … FOR UPDATE` в той же транзакции,
  что и сама запись — не по своей строке (как `freezeWhen`), а по строке,
  которую называет `object`. Гонка, которую это закрывает: параллельная
  архивация дата-рума обязана взять тот же лок на ту же строку перед тем, как
  записать `status` (это следует из `freezeWhen`/`transitions` самого
  дата-рума, не из этого ключа) — один из двух писателей всегда ждёт другого.
- **Приложение исключено по умолчанию** (`allowApplication` по умолчанию
  `true`) — то же исключение Б5, что у `writeRequiresParentAccess`:
  автоматизации приложения пишут от токена без `$me`. `allowApplication:
  false` закрывает и этот путь, когда архив обязан быть дном без исключений.
- **Создание** — тот же хук, без лока по своей строке (строки ещё нет):
  проверяется только значение FK, который вставка собирается записать;
  родитель так же лочится.
- **Жёсткое удаление (`delete`, не мягкое) этим ключом не закрыто** — та же
  граница, что у `freezeWhen` и `transitions`: обе проверки идут через
  `assertOnemaWriteInvariantsAreSatisfiedUnderLock`, который вызывается там,
  где есть `setColumns` или запись `deletedAt`, а у жёсткого удаления нет ни
  того, ни другого (как и раньше, мягкое удаление/восстановление — обычная
  запись `deletedAt` и ловится).

### Тесты

  — создание под замороженным/активным родителем, редактирование под уже

  под локом.
- Юнит: `validate-onema-access-rules-against-metadata.util.spec.ts` — четыре
  новых теста (валидный рецепт, чужой объект, FK не туда, поле не того
  объекта), по образцу существующих тестов `writeRequiresParentAccess`.
- Юнит: `parse-onema-access-rules.util.spec.ts` — все 40 построений
  `OnemaAccessRules` в файле получили `writeFrozenByParent: {}` (ключ обязателен
  в схеме), механически, без изменения семантики тестов.
- Интеграционный: `test/integration/graphql/suites/onema-access/onema-write-access.integration-spec.ts`,
  блок `"a child frozen by its parent's state (ONE-115)"` — `company`/`person`
  как заместители родителя/дочернего (как `person`/`company` уже служат
  заместителями в блоке заморозки выше); `company.name` играет роль
  `onemaDataroom.status`, потому что у стандартного объекта нет поля статуса.
  Семь сценариев: создание под замороженным/активным родителем, правка под
  уже замороженным, перенос прочь/на замороженного родителя (оба направления),
  правка под активным, мягкое удаление под замороженным.

**Не перепроверено end-to-end**: исключение приложения
(`allowApplication`/`isOnemaApplicationActor`) — только юнит-тестом с мок
`authContext`, не интеграционным сценарием с реальным токеном приложения.
Юнит-покрытие точное (та же функция, тот же код путь, что видит прод), и
заводить в интеграционном сьюте отдельную фикстуру-приложение ради этого не
стал — решение по объёму задачи, не найденный пробел.

## Прогон

Хост был занят параллельной установкой `node@24` другими воркерами
(конкурирующие `brew install node@24` в соседних worktree) — `yarn install`
в этом worktree не смог пройти постинсталл-проверку версии Node (нужен
`^24.5.0`, на хосте долго не было ни одной). Вместо повторной установки (это
только добавляло гонку) прогнал тесты так: `node_modules` этого worktree уже
были слинкованы более ранним (неудавшимся только на самой последней проверке)
`yarn install`, не хватало лишь собранных `dist` воркспейс-пакетов
(`twenty-shared`, `twenty-emails`) — скопировал их из уже собранного соседнего
worktree (`onema-twenty-wt-114`, тот же коммит `origin/main`, идентичный
`yarn.lock`) и прогнал `jest` текущим `node` (v26.7.0) напрямую, в обход
`yarn`/его проверки версии (она — отдельный констрейнт `yarn.config.cjs`,
а не ограничение рантайма; `jest`/`tsc` её не вызывают).

- `NODE_ENV=test NX_DAEMON=false npx jest --config jest.config.mjs onema-access --maxWorkers=2`
  — **19 сьютов, 359 тестов, все зелёные** (включая новый
  `assert-onema-write-is-permitted-by-parent-state.util.spec.ts` и расширенные
  `load-onema-access-rules.util.spec.ts`/`parse-onema-access-rules.util.spec.ts`/
  `validate-onema-access-rules-against-metadata.util.spec.ts`).
- `NODE_ENV=test NX_DAEMON=false npx jest --config jest.config.mjs twenty-orm/repository --maxWorkers=2`
  — 6 сьютов, 48 тестов, все зелёные (`workspace-repository.spec.ts` и соседи
  не задеты правкой двух точек встраивания).
- `NODE_OPTIONS="--max-old-space-size=8192" NX_DAEMON=false npx tsc -p tsconfig.json --noEmit`
  — те же ошибки окружения, что без моих правок (непостроенные `dist` других
  пакетов — `twenty-sdk`, `twenty-client-sdk`, нерезолвящиеся типы
  `@file-type/pdf`/`@lingui/message-utils`, и одна предсуществующая `TS2339` в
  `parse-onema-access-rules.util.ts:134` — воспроизвёл `git stash` на чистом
  `origin/main`, она есть и без этой задачи). Новых ошибок типов в изменённых
  или новых файлах нет.
- Интеграционный прогон (`onema-write-access.integration-spec.ts`, контейнеры
  `onema-it-pg`/`onema-it-redis`, сброс+пересев базы) — **не выполнен** в этой
  сессии: требует намного большего по времени поднятия стенда (сборка сервера,
  Docker Postgres/Redis, миграции, сид), а хост всё ещё был занят гонкой
  параллельных `brew install node@24` когда до этого шага дошло время. Блок
  `"a child frozen by its parent's state (ONE-115)"` написан и вычитан по
  образцу соседних блоков (`freezeWhen`, `writeRequiresParentAccess`) в этом же
  файле, но живого прогона на Postgres нет — следующая сессия или ревью должны
  это прогнать перед мержем.

## JSON для apps/onema/access-rules.json (onema-os)

Добавить секцию `writeFrozenByParent` (её в файле ещё нет — значит на верхнем
уровне, рядом с `writeRequiresParentAccess`/`transitions`). Поля — из реальных
объектов onema-os (`src/objects/dataroom-member.object.ts`,
`src/objects/dataroom-acceptance.object.ts`: обе связи на дата-рум названы
`dataroom`, `joinColumnName: 'dataroomId'`; `onemaDataroomItem` уже ссылается
на дата-рум тем же полем, это видно по существующему условию
`"parent": {"foreignKey": "dataroom", "object": "onemaDataroom"}` во всех трёх
дочерних объектах секции `objects`). `allowApplication` не указан — остаётся
умолчание `true`: домен-функции onema-domain (`archiveDataroom`,
`dataroom-accept-stage` и т.п.) продолжают писать эти объекты от токена
приложения, как и раньше, пока явно не решено иначе.

```json
"writeFrozenByParent": {
  "onemaDataroomItem": [
    {
      "foreignKey": "dataroom",
      "object": "onemaDataroom",
      "field": "status",
      "equals": "ARCHIVED"
    }
  ],
  "onemaDataroomMember": [
    {
      "foreignKey": "dataroom",
      "object": "onemaDataroom",
      "field": "status",
      "equals": "ARCHIVED"
    }
  ],
  "onemaDataroomAcceptance": [
    {
      "foreignKey": "dataroom",
      "object": "onemaDataroom",
      "field": "status",
      "equals": "ARCHIVED"
    }
  ]
}
```

Это закрывает ровно дыру, описанную в
`docs/handover/2026-10-10-dataroom-archive-and-errors.md` («что НЕ сделано»):
прямой REST/GraphQL PATCH материала, участника или приёмки человеком теперь
физически отказан на уровне движка, а не только через `canEdit` в домене.
Применение этого JSON к `apps/onema/access-rules.json` и включение на стенде —
отдельная задача (как ONE-121 включал правила переходов смет на стенде 2), не
эта: эта задача закрывает только форк.
