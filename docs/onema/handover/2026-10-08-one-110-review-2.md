## 1. `requiredObjects` — обязательные объекты

Замечание: опечатка в имени объекта теперь ловится сверкой с метаданными, но
**валидный пустой или неполный `objects`** — нет. Объект, которого в файле
просто нет, работает по правам апстрима, и это неотличимо от «правило ещё не
написали».

Сделано: в файле правил появился обязательный список `requiredObjects`.
Объект из списка, у которого нет записи в `objects` или чья запись не
называет ни одной роли, отвергает **весь файл**: при старте процесс не
поднимается, у работающего состояние уходит в `failed`, то есть каждый
запрос получает `1=0`, а причина пишется `logger.error`. Точечно закрыть
один объект нельзя по той же причине, что и при опечатке: файл в этом
состоянии не описывает политику целиком, и чему верить — неизвестно.

Ключ обязателен сам по себе: «ничего не обязательно» пишется как `[]`
явно. Забытый ключ был бы ровно тем же молчаливым умолчанием этажом выше,
ради которого всё это и делается.

Проверка живёт в `parse-onema-access-rules.util.ts` (рядом с циклами и
глубиной), а не в сверке с метаданными: она чисто структурная, файлу для неё
не нужен воркспейс, и чем раньше отказ — тем он громче. В типе
`OnemaAccessRules` поле необязательное, в схеме — обязательное: правила,
собранные в памяти (тесты, тестовый мост), файла, в котором можно забыть
ключ, не имеют. Мост дописывает `requiredObjects: []` при сериализации.

`onema/access-rules.example.json` перечисляет все четыре объекта примера.

## 2. Тестовая подмена правил

Замечание: override лежал в фиксированном `path.join(os.tmpdir(),
'onema-access-rules.testing-override.json')`, имел приоритет над боевым
файлом и обходил release gate — то есть файл, подброшенный в temp, мог
задать права работающему серверу.

Сделано:

- путь вычисляется **только при `NODE_ENV=test`**; вне тестов функция
  возвращает `undefined`, и ветка override в `getOnemaAccessRulesState`
  просто не существует — боевой `ONEMA_ACCESS_RULES_PATH` перебить нечем;
- `setOnemaAccessRulesForTesting` вне `NODE_ENV=test` бросает
  `OnemaAccessException`, а не ставит молча правила, которые никто не
  прочитает;
- имя файла содержит pid процесса, файл пишется с `mode: 0o600`: общий на
  хост путь позволял бы одному прогону (или чему угодно, что пишет в temp)
  задать права другому.

Почему вообще файл, а не кэш в памяти: интеграционный тест поднимает
приложение в `globalSetup` Jest, а управляет им из тестового файла. Это один
процесс ОС (`maxWorkers: 1`), но разные vm-контексты Jest — общий у них
только диск. На pid это и опирается; если Jest когда-нибудь разведёт стороны
по разным процессам, интеграционный тест упадёт заметно, а не тихо откроет
данные.

## 3. `shouldBypassPermissionChecks` — принято, аудит в ONE-113

Остаётся как есть и в ONE-110 не трогается. Это единственный доверенный
обход, его запрашивает вызывающий явно при создании репозитория, и он
возвращает управление раньше, чем хук вообще вызывается. Проблема не в самом
флаге, а в том, что никто не считает его вызовы: в ONE-113 запланированы
инвентаризация всех мест и CI-проверка на новые обращения мимо хука. До тех
пор `ONEMA_ACCESS_ENFORCE=1` стоит только на стенде — тот же release gate.

## 4. Окно до 5 с при перечитывании — принято осознанно

Между процессами остаётся окно до `ONEMA_ACCESS_RULES_RELOAD_INTERVAL_MS`,
в котором часть серверов и воркеров работает по прежней версии правил. Это
не регресс относительно альтернативы: обязательный скоординированный
рестарт сервера и N воркеров сам по себе не атомарен, его окно больше и
ничем не ограничено сверху, и ничто не замечает процесс, который не
перезапустился. Версия правил (12 символов sha256) пишется в лог каждым
процессом, так что «кто по каким правилам работает» — проверяемый вопрос.
Сузить окно — вопрос значения константы, а не схемы; отдельного тикета не
заводим.

## Тесты и прогон

**Юнит — 666 тестов, зелёные** (`onema-access` и `twenty-orm` вместе; в
`onema-access` 63, было 61).

Новое: файл без `requiredObjects` отвергается; обязательный объект без
правила и с пустым правилом → `1=0` на весь запрос; объект, которого никто
не требовал, по-прежнему может быть без правила; override не читается и не
пишется вне `NODE_ENV=test`; override не перебивает боевой файл в
production; файл override лежит по пути с pid, а не по общему.

**Интеграционный — 12 тестов, зелёные** (было 11). Добавлен: обязательный
объект без правила прячет и `company`, и `person` — объект, которого в
правилах нет вовсе и который иначе остался бы на правах апстрима.

Прогон тот же, одноразовые контейнеры `onema-it-pg` и `onema-it-redis`
(удалены после). Две новые грабли:

- пришлось поднять heap: `NODE_ENV=test npx jest --config
  ./jest-integration.config.ts` падает в OOM на дефолтных 4 ГБ при загрузке
  приложения в `globalSetup`; с `NODE_OPTIONS=--max-old-space-size=8192`
  проходит;
- `nx database:reset` по-прежнему тянет `twenty-ui:build` с падающим
  `vite-plugin-checker` (обход временный, не коммитится).

```bash
docker run -d --rm --name onema-it-pg -p 5432:5432 \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=default postgres:16
docker run -d --rm --name onema-it-redis -p 6379:6379 redis:7
docker exec onema-it-pg psql -U postgres -c "CREATE DATABASE test;"
npx nx build twenty-shared --skip-nx-cache
NODE_ENV=test npx nx database:reset twenty-server
NODE_ENV=test NODE_OPTIONS=--max-old-space-size=8192 \
  npx jest --config ./jest-integration.config.ts --testPathPattern onema-row-access
```

Соседние прогнаны и зелёные: интеграционные `relation-join-rls`,
`permissions-on-relations`, `twenty-orm` (9 тестов).
